# Round 1 Proposals

## Proposal A

**Summary:** Ship an explicit, transactional lineage bridge to a unified schema while retaining both reset contracts, enforcing shared operation ownership, and separating notification resource location from verified pane selection.

**Rationale:** The migration runner selects and skips steps solely by version (src/store/migrate.rs:501,639), but main and dev assign different migrations to 38–39 (src/store/migrate.rs:394–436); therefore recognize supported lineage through migration names plus validated table columns/constraints, reject inconsistent combinations without mutation, retain dev 38–43 as the canonical sequence, and bridge main 38/39 atomically to 44 after a verified backup, preserving original migration provenance, landing payloads and legacy reservation bytes in a distinct story_reset_reservations table without exposing an intermediate version rewind. Fresh and dev stores should reach the same schema through additive migration 44; preserve completed typed receipts and pending recovery records, and replace ambiguous version-based capability assumptions such as src/store/sqlite/landing.rs:11 with lineage-aware schema validation. Keep native reset's explicit force and awaiting/branch preservation (src/service/reset.rs:92,205–210) separate from typed dashboard destruction, but enforce pairwise exclusion among both resets, engine reset and landing at transactional admission and final commit, with database constraints/triggers protecting ownership from bypass writes; retain dispatch/verifier exclusion and make typed cleanup inherit the same WorkspaceLock through final persistence instead of relying only on its token lock (src/service/story_reset.rs:137–153). Notification should first resolve the recorded lease/server/worktree without selecting an active pane, then verify and immediately revalidate one exact process destination, because the current inactive-pane filter and selected-pane cwd refusal prevent that supported case (src/service/resources/tmux.rs:89; src/service/resources/mod.rs:673), while certification must still pass through durable landing authority and retain dev generation/withdrawal guards. Minimum release evidence is populated upgrades from shared schema 37, main 38/39 and every dev 38–43 boundary, exact preservation and operational recovery of pending journals plus completed receipts, restored-backup recovery, injected bridge rollback and concurrent/repeated migration, rejection of inconsistent lineage, both-order reservation races and deletion protection, native-versus-card reset behavior including surviving cleanup children, and real composed notification tests covering inactive verified panes, recorded nonambient sockets, ambiguous identities and pane/process replacement; these tests were not run in this read-only review.

**Risks:** The greatest risk is relabeling or partially migrating a main store into dev's version sequence while losing durable operation authority or causing an old reservation to acquire the dashboard reset's destructive semantics.

**Confidence:** high

## Proposal B

**Summary:** Ship an explicit, transactional schema-lineage bridge, retain both reset contracts behind shared transactional ownership and workspace locking, and separate notification location discovery from verified process targeting.

**Rationale:** The actual main schema stores reservations in story_resets.reservation, not stories.reset_json (HEAD:src/store/schema/0039_story_reset.sql:2), whereas dev uses story_resets.record_json (src/store/schema/0043_story_resets.sql:2): retain dev migrations 38–43 and add canonical 44, recognizing each supported historical state through migration names plus structural checks, verifying a backup before mutation, and bridging main atomically under BEGIN IMMEDIATE by preserving its landing rows, renaming its reservation table, installing missing dev structures, and recording canonical history plus original lineage without an observable version rewind; reject inconsistent or unknown combinations and replace numeric capability assumptions such as src/store/sqlite/landing.rs:10 with validated schema capabilities. Native reset explicitly renews force authorization and restores prior awaiting state (src/service/reset.rs:92,205), while card reset clears awaiting and removes its local branch (src/service/story_reset.rs:216), so keep these public contracts and recovery journals separate, but enforce pairwise exclusion among native reset, active card reset, engine reset, and landing at the final store transaction boundary, including imports and deletion, retaining every unresolved reservation rather than converting or clearing it. Card reset currently holds only a token-specific flock before quiescence and cleanup (src/service/story_reset.rs:137–179); after quiescence it must acquire the same repository/story WorkspaceLock used by native reset, revalidate pinned identities under that lock, pass ownership into destructive subprocesses, and retain it through completion, while preserving no-checkout operation, exact inode/Git/lease checks, and protected-artifact refusal; verification must likewise preserve certify→durable landing intent→external merge→reconciliation, with generation/block-revision checks and certification never interpreted as merge completion. Notification requires a location-only resource contract carrying canonical repository/worktree and recorded socket/window evidence, followed by enumeration of all panes and exact provider/process identity selection, then revalidation before interrupt, paste, and submit: globally changing active-pane selection would alter unrelated cleanup contracts, while the present active-only filter and cwd rejection demonstrably precede valid inactive-agent selection (src/service/resources/tmux.rs:89; src/service/resources/mod.rs:673). Minimum release evidence is executable upgrade coverage for shared schema 37, main 38/39, every dev 38–43, and fresh stores with populated pending operations and completed receipts; rollback/reopen/concurrent-upgrader and malformed-lineage cases; bidirectional reservation races, lock inheritance after parent death, and retry tests for both reset contracts; stale-generation/blocker and uncertain-merge recovery tests; and composed real-resource notification tests for inactive verified agents, recorded nonambient sockets, multiple matches, changed processes/panes, dead-pane identity, and refusal without respawn, followed by the central full suite.

**Risks:** The greatest risk is preserving both reset implementations while leaving even one admission, import, cleanup, or completion path outside the shared ownership invariant, allowing one operation to delete resources still owned by another.

**Confidence:** high
