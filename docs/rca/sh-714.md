# SH-714: Retained infrastructure history hid a running verifier retry

- **Date**: 2026-09-13
- **Severity/Impact**: In v2.4.2, an authenticated retry could appear stalled in story progress and show waiting stories as held in dashboard and CLI status. The display misrepresented current execution; no false certification or automatic interruption was observed.
- **Status**: Fixed in `6385eff941ec36a25abac9216b52e68e73e4048d`; full-suite verification and merge remain with the centralized verifier. Installed-system validation is pending.

## Summary

After an infrastructure failure, a retry could pass merge preflight and enter its
release gate while status still reported the prior failure as current. The
durable incident correctly preserved the retry budget, but status treated its
presence as unconditional blocking authority. The fix authenticates the active
retry once and shares the resulting classification across status consumers,
without deleting history. Historical failure evidence and current execution
authority require separate contracts.

## Root cause & trigger

The trigger was recovery from a retryable infrastructure failure: the next
attempt reached verification while its incident remained stored for bounded
retry accounting.

| Causal link | Evidence |
|---|---|
| Retain failed-attempt history | Infrastructure incidents survive admission and retain counts until settlement. Clearing at retry admission would reset the budget. |
| Treat all history as current authority | The incident-first branch in `src/daemon/verification_progress.rs` suppressed matching gate progress; `src/daemon/verification/status.rs` independently counted every incident as held work. |
| Publish misleading state | The regression `authenticated_retry_projects_running_without_erasing_its_failure_history` received Stalled instead of Running and propagated the incident to queued work. |

**ODC classification:** Checking / Incorrect; trigger: recovery/error path.
Stale journal identity does not explain the reproduced specimen: its generation
and attempt UUID matched the active owner, and removing only the incident
argument restored Running.

## Contributing factors

- Durable failure accounting and current blocking state shared one presence check.
- Existing journal authentication allowed readable legacy progress; legacy evidence alone cannot prove that a particular retry recovered.
- A prepared progress comment could outlive its incident snapshot or cancellation state. Ownership and generation checks alone did not reject every stale publication.

## The fix

Commit `6385eff94` applies a **SURGICAL** correction at the projection boundary.
Admission captures the incident ID and attempt count. `AttemptEvidence` in
`src/daemon/verification/evidence.rs` reads and folds one owned journal; an
unchanged, nonhalted retryable incident becomes history only for matching
project, story, generation, UUID, and ordered explicit preflight/gate evidence.
`GateProgress::reached_verification_gate` rejects malformed or implied lifecycle
proof. Raw output cannot establish recovery.

CLI, dashboard data, story status and progress publication share the
classification. `VerifierStatus.incident_is_current` exposes it while preserving
the incident record. Publication rechecks ownership and cancellation, then
compares the incident in the generation-guarded store transaction. A later
failure regains authority immediately. Retry ceilings, halt acknowledgement,
certification, settlement and cleanup behavior remain unchanged.

## Preventative action — killing the class

| Guard | Contract exercised |
|---|---|
| `authenticated_retry_projects_running_without_erasing_its_failure_history` in `tests/verification_retry_progress.rs` | Production status, REST, CLI/load-context and comments agree while durable failure history remains unchanged; stale identity and newer failures retain authority. |
| `real_head_convergence_retry_reports_running_then_preserves_red` and `real_head_convergence_retry_reports_running_then_preserves_green` in `tests/verification_retry_shell.rs` | The real shell verifier fails local head convergence, retries into an observable gate, then preserves each verdict's settlement. |
| `only_unchanged_retry_incident_for_exact_owned_submission_is_history` in `src/daemon/verification/evidence.rs` | Ownership, generation, UUID, disposition, halt and incident-version mismatches cannot establish recovery. |
| [Recovered-retry contract](../spec/verifier-observability.md#recovered-infrastructure-retries--sh-714) | Shared evidence, publication fences and operational limits are explicit. |

Focused validation passed **250 Rust checks and 24 browser tests** (12 each in
Chromium and WebKit), plus targeted Clippy with warnings denied, formatting and
diff checks. Three isolated mutations failed as expected: restored incident-first
precedence, removed UUID validation, and removed incident-count validation.
An initial shared-target artifact contamination invalidated those early mutation
runs; the accepted runs used separate source and target artifacts and a passing
clean baseline.

The impacted-test selector returned `ALL` because its baseline lacked a coverage
map. Only new and directly impacted checks ran here; the centralized verifier
owns the full suite and merge. The installed inspection workaround remains until
a containing installation passes installed recovery validation.

## Lessons

Retaining an incident is a policy obligation, not proof that the current attempt
is blocked. Authenticate recovery from lifecycle evidence, preserve the budget,
and compare the evidence's authority again when publishing. Passing source tests
does not establish that an installed verifier contains the fix.
