# Native shared-project recovery

SH-871 adds a project-scoped recovery path for a supported native Rust contrast.
Two candidate failures and two pinned-control failures must match the original
assertion under equivalent detector, toolchain, fixture and resource conditions.
The native comparison must explicitly settle its resources. Serialized assessor
observations cannot enroll recovery or grant certification.

Enrollment retains the original submitted generation. The owner key includes the
project, check, assertion signature, pinned base, control tree, detector, command,
toolchain, fixtures and resource-policy identity. Candidate commits and output
paths remain individual observation facts. The existing database ownership index
on project, fault code and locus holds the SHA-256 key; no schema migration is
needed. The optional versioned state extension preserves legacy records and
makes an older strict decoder refuse shared records rather than execute them.

New project engine admissions and ordinary verification admissions wait while
this owner is active. The explicitly managed repair can enter central verification
under the existing three-changed-input limit. Project proof never pauses another
project. The scope assessor must select a separate repair or an explicit external
prerequisite; the unrelated author submission cannot be selected as the repair.
Existing durable delivery epochs preserve uncertain calls without replaying them.
A raw fault encountered by that repair remains in its original lineage.

Different fault keys remain distinct. A claimed assessor may use a version-two
separate-story decision with `join_recovery: { recovery, revision }` instead of
`repair` to assign a second fault to the existing repair. This is a semantic
decision, not symptom-based deduplication. The target must be an active native
shared owner in the same project, with no unsettled delivery, live attempt,
certification, landing, or resource ambiguity. Followers cannot own other
followers, dispatch another agent, or spend a separate attempt budget. Ordinary
dependency-cycle checks still apply. Both faults must authorize that repair
before queue selection, work delivery, or gate admission can proceed.

The canonical owner retains the aggregate three-input budget across restart.
Every joined fault's native archives are rechecked at effect and gate admission.
The repair submission must be newer than all enrolled fault generations. A
certified landing writes matching release receipts to all joined records in the
same transaction; each retained submission still clears only its own exact hold
and must undergo fresh verification. Status exposes the canonical attempt count
on each participating fault. A stale or cyclic coordination pointer fails closed.

Only a certified repair landing or the existing operator prerequisite attestation
can release the owner. A single atomic transaction rechecks the exact original
state, generation, labels, PR identity, operator policy, reset/landing holds,
recovery-owned awaiting event, original attribution snapshot and retained native
output digests. It retires only a single proved component and records a readmission
receipt with the release event. Mixed or changed evidence stays held. Repeated
reconciliation is read-only after the receipt. This is queue eligibility for a fresh
current-base merge and gate; it is neither an author resubmission nor certification.
The ordinary verifier's private pinned-input callback enforces the original
submitted head again before executing a gate, while allowing the base to advance.
Changed head or authority produces the ordinary durable verification refusal
diagnostic. A retained generation cannot enter a batch (which lacks that callback)
or bypass its fresh certification obligation when verification is stopped.

Recovery JSON status includes the original start, elapsed wall time including
pauses, cumulative native diagnosis milliseconds, owner, affected stories,
attempt counts and the next action. None of the timing counters is refunded on
retry or daemon restart.

## Remaining SH-871 acceptance

This source slice does not supply a host-wide proof adapter, host repair effects,
or single-submission integration smoothing. Such faults retain their existing
holds. The existing batch-only smoothing allowlist does not authorize a different
scope. No credentials, host deletion commands or arbitrary shell repair hooks are
introduced. Those remaining acceptance items need a separately reviewed concrete
adapter and policy boundary before the whole story can be considered complete.
Different active faults remain held until their explicit decisions authorize a
common repair. Competing live repair owners require ownership reconciliation;
the coordinator does not silently revoke their work or adopt their effects.

All tests authored for this slice are unrun until the coordinator schedules the
validation lane. Native fixture tests use their existing bounded broker and tiny
Rust comparison workloads; implementation work does not run production engines.
